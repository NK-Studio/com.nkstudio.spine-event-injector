# 내보내기 PoC 연구 기록

Spine 없이 `.spine`을 JSON·`.skel`·atlas로 내보내는 PoC(`export_poc/`)의 구조와, 실제 Spine 결과와 비교해 알아낸 규칙을 정리한다. 사용법은 [`SPINE_EXPORT_USAGE.md`](SPINE_EXPORT_USAGE.md).

- 모든 규칙은 **Spine CLI 내보내기 결과와의 비교**로 얻었다. 편집기 본체는 풀거나 디컴파일하지 않았다([`SPEC.md`](SPEC.md) §0).
- 표본은 Spine 공식 예제 프로젝트 전부(4.2판 16개, 4.3판 17개)와 버전별 spineboy 저장본이다.

## 1. 구조

| 파일 | 하는 일 |
|---|---|
| `anim_clean.py` | Spine의 "애니메이션 정리"와 같은 키 정리(모델에 적용) |
| `project_reader.py` | 이벤트 주입 PoC의 해석기(`poc/spine_event_poc.py`) 위에서 참조 따라가기, 버전별 필드 키 통일, 잎 값 꺼내기 |
| `model.py` | 프로젝트 그래프 → 버전 무관 모델(뼈·슬롯·제약·스킨·이벤트·애니메이션). 지원하지 않는 기능은 `ModelError` |
| `json_writer.py` | 모델 → JSON |
| `binary_writer.py` | 모델 → `.skel` |
| `atlas_packer.py` | PNG 읽기/쓰기(표준 라이브러리), 잘라내기, MaxRects 배치, `.atlas` |
| `spine_export.py` | 명령줄 |
| `check_against_spine.py` | Spine CLI 결과와 비교 |

뒤쪽 편집기 상태(내보내기 설정 등)에서 스키마가 막혀도 프로젝트의 스켈레톤 목록을 끝까지 읽었으면 그 결과를 쓴다(`Project.load_partial`).

## 2. 프로젝트 파일에서 읽는 값

- 태그 번호는 4.0~4.3 공통이고 키 모양만 다르다(`12`, `t12`, `d12`, `1:12`).
- 키프레임 두 방식.
  - 옛 방식: Timeline 20 / Keyframe 115, 태그 필드, 곡선 1 linear · 2 bezier · 3 stepped
  - 새 방식: Timeline 132 / Keyframe 133, 고정 배치, flag 0 linear · 1 bezier · 2 stepped (4.3.04+ 핸들은 조건부 블록)
- 타임라인 종류: 0 rotate, 1 translate, 2 scale, 3 shear, 4 color(7채널), 5 attachment, 6 deform, 7 ik[mix, softness, stretch, compress, bend], 8 transform(6 mix), 9 경로 위치, 10 경로 간격, 11 경로 mix, 12 event, 13 드로우 오더, 14 translatex, 15 translatey, 22 시퀀스, 27 물리 wind, 36 물리 wind(전체), 40 슬라이더 mix.
- 경로 제약: 4 위치, 12 간격, 10 회전, 8·6·23 mixRotate·X·Y, 14 간격 모드(1 length, 2 fixed, 3 percent, 4 proportional), 15 회전 모드(1 tangent, 2 chain, 3 chainScale), 16 위치 모드(1 fixed, 2 percent).
- 물리 제약: 4 = 1/fps, 5 x, 6 y, 7·9 회전·전단 저장값(a, b → rotate = a·t, shearX = b·t, t = a/(a+b), a가 0이면 t = 1), 8 scaleX, 10 inertia, 12 strength, 14 damping, 16 mass, 18 wind, 20 gravity, 23 mix, 25~31 Global 플래그, 33 limit.
- 시퀀스: 1 start, 2 count, 3 digits, 4 setup(zigzag). 영역 이미지는 RegionAtt 15, MeshAtt 36에 있다. 타임라인은 슬롯과 첨부를 함께 가리킨다.
- 슬롯·제약·스킨·애니메이션 이름은 폴더 경로를 포함한다(슬롯 16, 제약 32, 스킨 5, 애니메이션 7 = 폴더). 애니메이션 태그 5가 0이면 내보내지 않는다.
- 정점 변형의 묶음 머리는 varint가 아니라 1바이트다(0x80도 나온다).
- 첨부 공통 태그 5 = Export 체크. 꺼져 있으면 첨부·설정 자세·deform·시퀀스 타임라인에서 빠지고, 첨부 키는 이름 없는 키로 남는다.
- 이벤트 타임라인은 이벤트 정의마다 따로 있다. 내보낼 때 시간순으로 합친다.
- 곡선은 채널별 float 5개 `[inX, inY, outX, outY, ?]`, 프레임 단위, `0x4f000000`이 미설정.
- 메시: hull은 경계 변 수. 가중치와 deform은 메시 뼈 수만큼의 조밀 배열이라 런타임 순서로 변환한다.

## 3. JSON 규칙

| 항목 | 4.0~4.2 | 4.3 |
|---|---|---|
| 숫자 | 자릿수 반올림(pos 2, scale 4, mix 3, time 4, 곡선 시간 3, uv·weight·deform 5, 변형 키의 mix 4). float32 값, double 곱, `floor(x*10^d+.5)`, Java `Double.toString` 표기 | float32 그대로 짧게(Dragon4 근사, 이웃 간격 3/4). 단 첨부 정점 좌표·가중치는 4.2와 같은 자릿수로 반올림 |
| 프레임 → 초 | `f32(frame * f32(1/fps))` | `f32(frame / fps)` |
| 기본값 생략(설정값·키프레임) | 반올림 후 비교 | 값 종류별 자릿수로 반올림해 비교 |
| 제약 | `ik`/`transform` 섹션 | `constraints` 목록, `properties`, 애니메이션엔 `ik`/`transform` 유지 |
| 정렬 | 슬롯·IK·변형·첨부 이름순(글자 단위 자연 정렬), 뼈는 프로젝트 순서 | 뼈도 이름순 |

- 4.0은 `deform` 섹션과 `name: null`을 쓴다.
- 값이 같은 두 키 사이의 곡선은 계단(`stepped`)으로 낸다(4.0~4.3 공통). 같다는 기준은 float32 1 간격 이내 또는 차이 1e-6 이내이고, 색은 8비트 값 비교다. 베지어는 손잡이가 1e-5 이내로 평평할 때만 계단이다. IK 키는 mix·softness만 보고 직선일 때만 계단이다.
- 4.3 변형 키는 제약에 없는 속성의 mix를 쓰지 않는다. 4.3 키의 mixScaleY 기본값은 1이다.
- deform은 앞뒤에서 설정 위치와 0.01 이내로 같은 값을 잘라낸다.

## 4. 바이너리 규칙

- 문자열 표: 프로젝트의 첨부 목록 순서로 이름·경로를 넣는다(자리표시자 포함). 4.0/4.1은 스킨·이벤트 이름도 끝에 온다. 참조는 같은 문자열의 **마지막** 번호.
- 필드: 4.0/4.1은 플래그 없는 차례 필드, 4.2는 플래그, 4.3은 통합 제약 목록(타입 0 ik, 2 transform, 플래그 상위 3비트 = 속성 수).
- 곡선은 "다음 키를 쓴 뒤 앞 구간 곡선"을 쓴다.
- 4.2.00~4.2.20의 IK 키 mix·softness는 앞 키 값을 쓴다(Spine의 동작을 그대로 재현).
- deform 잘라내기는 정확히 0인 값만(JSON과 다르다).
- 해시는 계산법을 몰라 본문 SHA-1 앞 8바이트로 채운다.
- 가중치는 5자리로 반올림한 값을 float으로 쓴다.
- 경로 제약 플래그: 4.2는 position | spacing<<1 | rotate<<3, 4.3은 skin | position<<1 | spacing<<2 | rotate<<4. 128 = 회전 오프셋 있음. 4.0·4.1은 플래그 없이 varint 3개와 float.
- 물리 제약: 1 skin, 2 x, 4 y, 8 rotate, 16 scaleX, 32 shearX, 64 limit, 128 mass. mass는 역수로 저장한다. fps는 1바이트.
- 물리 타임라인 번호는 1부터(0 = 모든 물리 제약). 슬라이더가 쓰는 애니메이션 번호는 애니메이션 목록 뒤에 온다.
- 슬라이더 max는 비필수 데이터가 있을 때만 쓴다.
- 4.3은 애니메이션 끝쪽이 드로우 오더, 드로우 오더 폴더(0), 이벤트 순이다.

## 5. Atlas 규칙

- 여백 2, 알파 3 초과로 잘라내기, 메시 이미지는 자르지 않는다.
- 미리 곱한 알파: `c * a // 255`(버림).
- `rotate:90`: 원본 (x, y) → 페이지 (r.x + y, r.y + w − 1 − x).
- 형식은 `bounds` / `offsets` / `rotate` 줄. 페이지 사이에는 빈 줄을 둔다. PMA를 끄면 `pma:true` 줄이 없다.
- 블리드(PMA 끔일 때만): 잘라낸 이미지의 완전 투명 픽셀 RGB를 주변 8칸 평균(정수 나눗셈)으로 채우기를 2회. 회차 안에서는 앞서 채운 값을 쓰지 않는다. 보이는 픽셀과 알파는 바뀌지 않는다. `spineboy`에서 투명 픽셀 316,041개 중 20개가 다르며, 규칙이 완전히 일치하지는 않는다.
- 에일리어스: 잘린 뒤 크기·오프셋·원본 크기가 같고, 완전 투명 픽셀 RGB를 뺀 픽셀이 같으면 합친다. 이름순 첫 영역을 싣는다. Spine의 추가 조건은 알아내지 못해 PoC가 조금 더 합친다(`cat.spine` 87묶음 / Spine 73묶음).
- 배치는 MaxRects(짧은 변 맞춤)로, Spine과 페이지 안 위치가 다르다.
- 속도: 빈칸을 쪼갠 뒤 새 조각만 포함 검사를 하면 결과는 그대로이고 계산은 크게 준다(안 쪼개진 빈칸끼리는 이미 서로를 포함하지 않는다). 영역 1322개 `cat.spine`에서 `pack_page` 1회 18.96초 → 0.26초, 내보내기 전체 8.9초, 옛 코드와 배치 동일.
- Spine의 팩은 더 빠른 알고리즘이 아니다. 같은 `cat.spine`을 Spine 4.2.43 CLI로 묶었을 때 14분이 지나도 끝나지 않아 중단했다(CPU 12분 이상). 공개된 libGDX MaxRectsPacker를 옮긴 실험은 spineboy에서 페이지 크기가 Spine과 달랐고(이 PoC와 Spine의 차이와 비슷한 수준), 페이지 크기 탐색 × 휴리스틱 5종 구조라 파이썬으로는 훨씬 느려 적용하지 않았다.

### `.skel` (2026-11-08)

PoC `.skel`을 Spine CLI로 다시 가져와(`-r`) JSON으로 내보낸 결과와, Spine 자신의 `.skel`을 같은 과정으로 처리한 결과를 비교했다. 숫자 차이 허용치는 0.0111(JSON 반올림 자릿수 경계)이다.

| 버전 | 비교 | 결과 |
|---|---|---|
| 4.0.64 | 9개 | 9/9 차이 0 |
| 4.1.24 | 12개 | 12/12 차이 0 |
| 4.2.43 | 14개 | 14/14 차이 0 |
| 4.3.26 | 17개 | 17/17 차이 0 |

해시를 뺀 바이트까지 같은 것은 52개 중 13개다. 나머지는 가중치 메시 정점의 float 끝자리 차이와 첨부 순서 차이다.

Unity(4.2 런타임) `.skel` 44개(PoC 30, Spine 14)는 전부 로드·렌더 성공, 예외·에러 로그 0. 프레임별 비교(20쌍)에서 정점 최대 차이 0.0000076, 첨부·드로우 오더·이벤트·색 차이 0. 뼈 값 차이는 chibi-stickers의 비활성 뼈뿐이었다.

Unity(4.2 런타임): 임포트 44개(PoC 30, 대조군 14) 전부 로드·렌더 성공, 예외·에러 로그 0. 4.2 JSON을 Spine 대조군과 프레임별로 비교(20쌍)해 정점·색·첨부·드로우 오더·이벤트 차이 0. 뼈 값 차이는 chibi-stickers의 그 스킨에서 비활성인 뼈(이전 값이 남은 것)뿐이었다. 4.3 JSON은 프로젝트 런타임이 4.2라 Unity에서 시험하지 않았다.

### 애니메이션 정리 `--clean` (2026-11-09)

규칙은 Spine CLI의 `-m` 전·후 JSON을 공식 예제, `cat.spine`, `tile_object.spine` 전체에서 비교해 얻었다(`export_poc/anim_clean.py`).

- 대상: 뼈(회전·이동·크기·전단), 색, 첨부, deform, 드로우 오더, 변형 제약, 경로 제약. IK·물리·슬라이더·이벤트·시퀀스는 정리되지 않는다.
- 값이 앞 키와 같고 구간이 평평하며 다음 키도 같거나 마지막이면 지운다. 정해지지 않은 곡선 손잡이는 값 높이로 본다.
- 설정 자세로 시작해 평평한 앞쪽 키는 변화 직전 키만 남긴다. 남은 키가 설정 자세 하나뿐이면 타임라인을 지운다.
- 첨부·드로우 오더는 앞 키와 같으면 지우고, 앞쪽의 설정과 같은 키도 지운다.
- 정리로 애니메이션이 짧아지면, 끝 시간에 키가 있던 타임라인 중 맨 뒤의 것에 마지막 키를 되살린다.
- 애니메이션 태그 9가 켜져 있으면 정리하지 않는다(`owl`의 `idle` 하나로 추정한 규칙).

| 검증 | 결과 |
|---|---|
| JSON vs Spine `-m` (4.2.43·4.3.26, 예제·cat·tile) | 스켈레톤 71개 전부 숫자 끝자리 외 차이 0 |
| `.skel` 크기 | `cat.spine` 4.3.26 252,002바이트로 Spine과 같음. alien-pro·owl-pro는 정리 전부터 있던 크기 차이가 있고 재임포트 비교는 같음 |
| `.skel` Spine 재임포트 비교 | 24건 차이 0 |
| Unity 4채널(몸·머리·표정·꼬리, `cat.spine`) | 2,610프레임에서 뼈·정점·색·첨부·드로우 오더 차이 0. 정리 안 한 파일은 첨부 175건, 뼈 최대 0.175, 정점 최대 0.038 차이 |

읽지 못하는 옛 베타 2개는 비교에서 빠졌다.

## 7. 모르는 것

- 스켈레톤 해시 계산법.
- 4.0~4.2 가중치 메시의 삼각형 순서 규칙(블록별 역순으로 보이나 미해독).
- 4.3 숫자 표기의 정확한 알고리즘.
- 4.3 IK 플래그 비트 일부와 IK compress/stretch 태그는 표본 값으로 추정한 것이다.
- `poc/schema/4.3.26.json`의 DirState·DirEntry 보강은 4.3.26 편집기 저장본에서만 확인했다.
- 물리 타임라인 wind 외 종류와 슬라이더 저장 필드 일부(표본 없음).
- 물리 rotate·shearX 환산식은 예제 저장본 4개 조합으로 맞춘 것이다.
