# `.spine` 4.2 프로젝트 포맷 관찰 원장

> 실측만 적는다. 가설은 **가설**이라고 표시한다. 확정되면 표시를 지우고 근거(표본 경로·오프셋)를 남긴다.
> 오프셋은 모두 **본문**(raw inflate 결과) 기준이다.

## 컨테이너

- raw deflate 스트림 하나(zlib 헤더·adler32 없음, 뒤에 남는 바이트 없음).
- level 6, windowBits -15, memLevel 8, 기본 전략으로 다시 압축하면 바이트 동일(spineboy-pro, diff-001 base/probe).

## 기본 타입 (관찰)

| 타입 | 인코딩 | 예 |
| --- | --- | --- |
| 문자열(ASCII, 길이 2 이상) | 바이트 그대로, 마지막 바이트에 `|0x80` | `footstep` → `66 6f 6f 74 73 74 65 f0` |
| 문자열 null / 빈 문자열 | `80` / `81` (**가설**, Kryo 규칙) | footstep 레코드의 `01 81` 후보 |
| float | 빅엔디언 IEEE754 | 1.0 `3f800000`, 1.5 `3fc00000` |
| 정수 | varint(7비트, LE 그룹), 부호 있는 것은 zigzag (**가설**) | int 7 후보 `0e` |

문자열 앞에 자주 붙는 `01`은 «null 아님» 표지로 보인다(**가설**).

## 이벤트 정의 — diff-001 (`research/diff-001-add-event`)

변형: 정의 `zz_probe {int:7, float:1.5, string:"hello"}` 추가, `run` 0.1초에 키 추가. 두 파일 모두 Spine 4.2.43 CLI import로 만들었다.

base (정의 1개):
```
0f 01 01 | 23 01 0a 03 00 0a 6c 04 09 00000000 08 00000000 06 01 81 00 03 02 01 "footstep" 04 00000000 05 05 07 01 | 01 00 02 03 03 01 "./images" ...
```

probe (정의 2개):
```
0f 01 02 | 23 01 0a 03 00 0a 6c 04 09 00000000 08 00000000 06 01 81 00 03 02 01 "footstep" 04 00000000 05 05 07 01
         | 23 01 0a 03 0e 0a 6c 04 09 00000000 08 00000000 06 05 00 03 02 01 "zz_probe" 04 3fc00000 05 01 "hello" 07 01
         | 01 00 02 03 03 01 "./images" ...
```

| O | 관찰 | 해석 상태 |
| --- | --- | --- |
| O-1 | `0f 01 NN`에서 NN이 정의 개수(01→02) | 유력 |
| O-2 | 레코드는 `23 01 0a 03 ..`로 시작하고 `07 01`로 끝남 | 유력 |
| O-3 | `04 <float>` = 이벤트 float 값(footstep 0, zz_probe 1.5) | 유력 |
| O-4 | `02 01 <string>` = 이름 | 유력 |
| O-5 | zz_probe의 `05 01 "hello"` = string 값. footstep은 `05 05`(빈 값의 다른 표현?) | 미확정 |
| O-6 | `09`, `08` 뒤 float 0 = volume/balance 후보. 단 volume 기본값 1이 안 보임 → 다른 필드일 수 있음 | 미확정 |
| O-7 | `0a 03 XX`: footstep `00`, zz_probe `0e`(= zigzag 7 = int 값?) | 유력(H2) |
| O-8 | `06 01 81`(footstep) vs `06 05`(zz_probe) | 미확정 |

## 참조 번호 밀림 (F7)

diff-001에서 정의 레코드 뒤쪽의 `20 0d 01 01 "portal-root"`가 `20 0f 01 01 …`로 바뀌었다. 객체 하나를 넣으면 이후 객체 ID가 zigzag 기준 +1 밀리는 것으로 보인다(**가설 H3**). 공통 접두 0x33, 공통 접미 143B라서 차이가 본문 전역에 퍼져 있다.

## PoC 해독 결과 (2026-11-08) — 파일 전체 해석 성공

자세한 사용법·결과는 [`poc/README.md`](../poc/README.md), 클래스·필드 표는 `poc/schema/4.0.07.json`(4.2)·`poc/schema/4.3.00.json`(4.3).

- 본문 구조: `varint ×3 · 문자열(포맷 버전) · 루트 객체 슬롯 · varint ×2 · 객체 슬롯…(에디터 상태, 끝은 null 6개)`. 포맷 버전 문자열은 4.2.22 저장본 `4.0.07`, 4.3.75-beta 저장본 `4.3.00`.
- 객체 슬롯 = `클래스 varint(0 null) · 참조 표지 varint(1 새 객체, n≥2 = n-2번 역참조) · 본문`. 필드 선언 타입이 구체 클래스면 클래스 없이 표지부터 쓴다. 참조를 추적하지 않는 클래스(4.3 변형 제약의 To 속성 등)는 표지 없이 본문만 쓴다.
- 본문 종류: 태그 필드(`필드 수 · (태그, 값)…`), 리스트(`크기 · 슬롯…`), 맵, 문자열, 열거형(varint), 고정 길이(색 4B, Vec3 12B), 배열(float[]는 슬롯 종류에 따라 길이 그대로/길이+1), 정점 변형(총 길이 · 128개 단위 묶음).
- **키 하나 = 새 객체 2개**(키프레임 + Event). 삽입 지점 뒤에서 새 번호 이상을 가리키는 역참조를 +2 하면 Spine이 그대로 연다(오라클 확인).
- 이벤트 키 시간 = 프레임 번호 float(F8 확인). int는 zigzag varint, float는 BE, string은 참조 추적 문자열 슬롯.
- 4.3은 참조 번호 표가 둘(A/B)이고, 키프레임이 타임라인 종류별 고정 배치(시간 · 값 · 곡선 5 float × 채널 · 플래그 · 종류별 객체)이며, 이벤트 정의는 처음 쓰는 키 안에 새 객체로 들어 있다.
- 4.2.43이 저장한 파일(포맷 문자열 `4.2.43`)은 아래 «4.2.43» 절에서 해독했다(`poc/schema/4.2.43.json`).

## 4.2.43 (2026-11-08) — spineboy 범위 해독 완료

표본: `research/diff-001-add-event/base.spine`·`probe.spine`, spineboy JSON을 `Spine -u 4.2.43 -i sb.json -o sb.spine -r`로 가져온 파일. 세 파일 모두 끝까지 읽히고 «다시 쓰기 = 원본» 바이트 일치. 실제 작업 파일 2개(스킨 포함)는 아래 «미해결»에서 멈춘다.

### 구조
- 머리: `varint ×3 · "4.2.43" · varint(스켈레톤 수: 1, 19 …) · Project(표지부터)`. 4.0.07·4.3.00에서도 이 varint는 1이라 «루트 클래스 1»로 읽혀 왔던 것.
- **참조 번호 표 둘(A/B)** — 4.3.00과 같은 배정에 더해 `SkelExtra`·`TimelineType`이 A. Vec3·List·Color·문자열·열거형(EnumX 등)·KeyList는 B.
  - 결정 근거: EventData.10 `6c 04`(A2 Folder), EventData.5 `05`(B3 ''), Slot.16 `6c 07`(A5 슬롯 폴더), Bone.32 `0d`(B11 EnumX), Bone.28 `13`(B17 'bone'), 이벤트 키의 정의 `05`(A3 EventData), Keyframe.timeline `a4 0e`(A1826 — TimelineType이 A여야 맞음).

- 정점 변형(`defvtx0`): `총 길이 · 묶음 수 · (머리 varint, 머리가 0이 아니면 float ×min(128, 남은 수))…` — 빈 변형은 `94 01 02 00 00`.

- 이벤트 키(종류 12): Event 필드는 4.0.07과 같은 태그(`1` 정의, `2` int zigzag, `3` float, `4` string, `5`·`6`).
- EventData: `3 0a 9 8 6 0 2 4 5 7` 순. `0a` = 이벤트 폴더(A), 필드 8·9는 가져온 파일에서 0.

## 패치 버전 공통 사항 (경계 탐색, 2026-11-08)

- **필드 순서는 표본마다 다르다.** 같은 버전 CLI로 같은 JSON을 가져와도 클래스 안 필드(특히 첨부의 상위 클래스 필드)를 쓰는 순서가 바뀐다. 그래서 어느 필드가 «필드 수 안»에서 중복(`d0`)으로 나오는지, 어느 것이 꼬리(`t4`, `t5` …)로 밀리는지도 표본마다 다르다. 스키마는 가능한 배치를 모두 담아야 한다. 다시 쓰기는 읽은 순서를 그대로 지키므로 영향이 없다.
- 첨부(메시·클리핑·바운딩박스·경로)에 필드 `35`(varint, 표본에서는 0)가 있다.
- **4.3 컨테이너**
  - 4.3.07부터: 스켈레톤 수 varint 뒤에 16바이트 ID(스키마 `root_pad: 16`).
  - 4.3.17부터: deflate 스트림 뒤에 20바이트 꼬리 `00 00 00 00 | 압축 길이(BE 4) | 8바이트 | 02 0b 02 0b`. 8바이트는 4.3.26 CLI가 로드할 때 검사하지 않는다(망가뜨려도 읽힘). `read_container`가 꼬리를 보관하고 `write_body(…, like=원본)`가 압축 길이만 고쳐 다시 붙인다. 레벨 6 재압축으로 원본과 바이트가 같다.

## 4.3 정식 (4.3.00 ~ 4.3.26)

4.3.75-beta(`4.3.00.json`, 태그 오름차순)와 달리 정식 빌드는 **필드 순서가 빌드마다 섞인다**(난독화된 필드 이름 순으로 보인다). 그래서 4.2.43처럼 «태그 = 키»로 읽되, 아래 차이를 스키마 옵션으로 다룬다.

- **묶음 방식(`groups`)**: 메시·클리핑·바운딩박스 첨부는 필드가 `[고유] [정점 공통] [첨부 공통 7개]` 묶음 순서로 나오고, 묶음 안 순서만 섞인다. 같은 태그가 묶음마다 다른 타입으로 다시 나오므로(0, 1, 4) 키는 `태그`·`1:태그`·`2:태그`로 나눈다. 앞의 필드 수 값은 실제보다 작게 적히므로(5개 차이) 쓰지 않고 «묶음마다 전부 읽으면 다음 묶음»으로 끝을 정한다.
  - 첨부 공통: 35 V, 1 S(이름), 4 T(Placeholder), 33 V, 32 T(Skin), 5 V, 0 T(Slot)
  - 클리핑 고유: 12 T(끝 슬롯), 13 V, 14 V
- **정점 공통 필드**: 4.3.00~4.3.03은 17개, 4.3.04부터 12개(태그 3, 4, 9, 10, 11이 빠짐).
- **타임라인 역참조(`tl_refs`)**: 4.3.00~4.3.02는 타임라인이 그룹을, 키가 그룹·타임라인을 역참조한다. 4.3.03부터 없다.
- **키 곡선(`curve_cond`)**: 4.3.00~4.3.03은 `시간, 값, 곡선 20바이트×곡선 수, 보간 플래그`. 4.3.04부터 `시간, 값, 플래그, [핸들 블록]`이다.
  - 플래그: 0 직선, 1 베지어, 2 계단
  - 핸들 블록 20바이트 = 들어오는 핸들 x·y, 나가는 핸들 x·y, 0. 쓰지 않은 핸들은 `4f000000`
  - 4.3.04: 그 키가 베지어일 때만 블록이 있다(`'own'`). 4.3.05부터: 그 키나 **앞 키**가 베지어일 때 블록이 있다(`true`, 앞 구간의 들어오는 핸들 때문)
- **컨테이너**: 4.3.07부터 머리 16바이트 ID(`root_pad: 16`), 4.3.17부터 20바이트 꼬리.
