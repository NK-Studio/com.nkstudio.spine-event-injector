## 4. 분석 방법과 경계

1. **본문 덤프·패턴 관찰**: 애니메이션 이름, 프레임 float(`41e00000`=7.0 등) 위치로 이벤트 키 구간을 찾았다.
2. **스키마 추론**: «클래스 → 본문 종류», «(클래스, 태그) → 값 타입»을 가설로 두고 본문을 처음부터 읽어, 모순(없는 객체를 가리키는 역참조, 클래스 불일치, 이상한 float·태그)이 나는 지점마다 가설을 고쳤다. 자동 탐색(후보 순서 휴리스틱 + 깊이 우선 탐색)과 사람의 바이트 판독을 섞었다. 파일 끝까지 모순 없이 읽히면 스키마 확정.
3. **주입 실험 → 오라클 판정**: 키를 넣은 파일을 Spine CLI로 내보내 비교했다.

경계: 분석 대상은 데이터 파일(`.spine`)과 Spine CLI의 문서화된 기능뿐이다. 에디터 본체(암호화 아카이브)는 열거나 풀지 않았다(MoonFrog 스펙 §0·§12-1 준수).

## 5. 확인된 포맷 사실

### 5-1. 컨테이너

- 파일 전체 = zlib 헤더 없는 **raw deflate 스트림 하나**, 뒤에 남는 바이트 없음.
- 본문을 level 6(windowBits −15, memLevel 8)로 다시 압축하면 원본과 바이트 동일.

### 5-2. 본문 전체 구조

```
varint varint varint  문자열(포맷 버전)  루트 객체 슬롯(Project)  varint varint  객체 슬롯…(에디터 상태, 끝은 null 0x00 여러 개)
```

포맷 버전 문자열이 스키마 파일 이름이 된다(`4.0.07`, `4.3.00`, `4.2.43`…).

### 5-3. 기본 인코딩

| 타입 | 인코딩 |
| --- | --- |
| varint | 7비트 LE 그룹, 상위 비트가 계속 표시 |
| int(이벤트 값) | zigzag varint (7 → `0e`) |
| float | 빅엔디언 IEEE754 (1.0 = `3f800000`) |
| 문자열 | Kryo 규칙: ASCII는 마지막 글자만 `|0x80`, 그 외는 «플래그 바이트+길이+1» 후 UTF-8. `0x80`=null, `0x81`=빈 문자열 |
| 이벤트 키 시간 | **프레임 번호를 float로** (7프레임 = `40e00000`). 초가 아님 |

### 5-4. 객체와 참조 번호 (핵심)

```
객체 슬롯 = 클래스 varint(0 = null) · 참조 표지 varint · [본문]
참조 표지  = 1 → 새 객체(다음 번호를 암묵적으로 받음) / n ≥ 2 → 이미 나온 n−2번 객체를 가리킴
```

- 필드 선언 타입이 구체 클래스면 **클래스 없이 표지부터** 쓴다(스키마의 `T` 슬롯).
- 번호는 **읽히는 순서**대로 매겨진다. 그래서 객체를 k개 끼워 넣으면, 삽입 지점 뒤에서 «새 번호 이상»을 가리키는 모든 역참조가 +k 되어야 한다.
- 역참조는 본문 전역에 흩어져 있고 필드 타입을 알아야만 위치를 알 수 있다 → **본문 전체 해석이 필수**.
- 실험 근거: 키 바이트만 복제해 넣으면 Spine 4.3.26이 `ClassCastException`으로 파일을 거부했다. 역참조를 다시 매기자 정상으로 열렸다.

### 5-5. 본문 종류(스키마 `kinds`)

| 종류 | 형식 |
| --- | --- |
| `tagged` | 필드 수 varint · (태그 varint, 값)… |
| `list` / `map` | 크기 varint · 객체 슬롯… (맵은 키·값 쌍) |
| `string` | Kryo 문자열 |
| `varint` | 열거형 값 하나 |
| `fixed4` / `fixed12` | 색(RGBA 4B), Vec3(12B) |
| `rfarray` / `rvarray` / `rsarray` | 길이 varint · float / varint / 2바이트 원소 |
| `farray` | 길이+1 varint · float (0 = null) |
| `boxfarray` | 길이+1 · 원소마다 표지 + float (4.3 변형 제약) |
| `defvtx` | 정점 변형: 총 길이 · 묶음 수 · (오프셋 varint, float ×128)… |
| `defvtx0` | 4.2.43 정점 변형: 위와 같되 묶음 머리 varint가 0이면 그 묶음은 float 없음 |
| `timeline` / `keyframe` | 4.3 전용 고정 배치(5-7) |
| `plain` | 태그 없이 정해진 순서의 필드 |

값 타입: `V` varint, `F` float, `S` 참조 추적 문자열, `O` 객체 슬롯, `T` 클래스 없는 슬롯, `N` 본문 없는 새 객체, `LO` 개수+객체 슬롯들.

참조 표(스키마 `tables`): `A`·`B`(번호를 받는 표), `none`(표지 없이 본문만), `flag`(표지 0/1만 — null 여부만 쓰고 번호를 받지 않음).

메시·클리핑·바운딩박스 첨부(VertexAttachment 계열)는 **필드 수 표시보다 실제 필드가 더 많다**(4.2는 4개, 4.3은 5개 더). 스키마 `tail`이 그 수다.

### 5-8. 이벤트 타임라인은 정의마다 하나

세 포맷 모두 이벤트 타임라인이 정의를 가리킨다(4.0.07은 Timeline 필드 `4`, 4.2.43·4.3은 종류 12의 추가 객체). 한 애니메이션의 이벤트 키는 **이벤트 그룹 하나(대상 null) 안에 정의별 타임라인 여러 개**로 저장된다. 4.2.43 차등 표본(probe)에서 Spine이 새 정의의 키를 같은 그룹의 두 번째 타임라인으로 저장한 것을 확인했다. 다른 정의의 키를 기존 타임라인에 섞어 넣으면 JSON 내보내기는 통과해도 에디터 구조와 어긋나므로, 주입기는 정의에 맞는 타임라인을 찾고 없으면 만든다.

## 6. 주입 알고리즘 (2차: 그래프 재직렬화)

1차는 «키 바이트를 복제해 끼우고, 삽입 지점 뒤 역참조를 +k»였다. 2차는 파일을 **객체 그래프로 읽고 Kryo 규칙대로 다시 쓴다.**

1. 본문을 스키마로 끝까지 읽어 객체마다 «원래 바이트 조각 + 슬롯(다른 객체를 담는 자리)» 나열로 만든다. 슬롯은 새 객체든 역참조든 «어떤 객체를 가리키는 자리» 하나로 다룬다.
2. 아무것도 고치지 않고 다시 쓰면 원본과 바이트가 같은지 확인한다(세 포맷 표본 모두 같음). 다르면 멈춘다.
3. 그래프를 고친다.
   - 키 추가: 같은 타임라인의 키를 복제(키 안의 Event만 함께 복제)하고 시간·정의·값을 바꿔 키 리스트에 끼운다.
   - 정의별 타임라인 추가: 같은 그룹의 이벤트 타임라인을 복제해 정의 참조를 바꾸고 키 하나만 남긴다.
   - 그룹 추가: 다른 애니메이션의 이벤트 그룹을 복제해 애니메이션 참조를 바꾸고 타임라인·키를 하나씩만 남긴다.
   - 정의 추가: 기존 정의를 복제해 이름·값을 바꾸고 스켈레톤 정의 목록과 이벤트 폴더 자식 목록 끝에 붙인다.
4. 다시 쓴다: 어떤 객체든 **처음 만나는 슬롯에서 본문째**(표지 1), 그 뒤로는 번호로 쓴다. 번호는 쓰는 순서대로 표마다 매긴다. 그래서
   - 역참조 번호 재계산이 따로 필요 없고,
   - 4.3에서 정의가 들어 있는 첫 키보다 앞에 키를 넣으면 정의 본문이 저절로 새 키 안으로 옮겨지고(L3 해결),
   - 4.3에서 앞쪽 애니메이션에 새 정의 키를 넣으면 정의 → 이벤트 폴더 → 기존 정의까지 Kryo가 쓸 순서 그대로 따라 옮겨진다.
5. 결과를 다시 읽어 «다시 쓰기 = 결과»인지 확인한 뒤 level 6 raw deflate로 새 파일에 쓴다.

빈 문자열은 Spine처럼 이미 있는 `''` 객체를 함께 쓰고, 새 키의 string 값은 정의의 문자열 객체를 함께 쓴다(4.2.43 차등 표본과 바이트 일치를 맞추며 확인).

## 8-2. 대안: JSON 수정 + CLI 애니메이션 교체 가져오기 (2026-11-08 시험)

바이너리를 직접 고치지 않고 `내보내기(JSON) → JSON에 이벤트 키 추가 → 임시 프로젝트로 가져오기 → 그 프로젝트에서 애니메이션만 교체 가져오기`로 넣는 경로.

```bash
Spine -u 4.3.26 -i 원본.spine -o out/ -e json
# out/<스켈레톤>.json의 animations.<이름>.events에 키 추가(time = 프레임/fps, 정밀도 유지)
Spine -u 4.3.26 -i edited.json -o tmp.spine -r
Spine -u 4.3.26 -i tmp.spine -o 원본.spine --from edited --to <스켈레톤> -a <애니메이션> --replace -r
```

| 시험 | 결과 |
| --- | --- |
| `-u 4.2.43`로 같은 명령 | **안 됨** — `-a`·`--from`·`--to`·`--replace`가 무시되고 스켈레톤이 통째로 하나 더 추가된다(애니메이션 가져오기 CLI는 4.3 기능) |
| 4.3.26, spineboy-4.3 run 8f(기존 정의) | 됨. 키 7·8·17(8.0 정확), 나머지 JSON 완전 동일 |
| 4.3.26, idle 5f(이벤트 없던 애니메이션) | 됨. 나머지 JSON 동일 |
| 4.3.26, **새 정의** hit + idle 키 | **안 됨** — `Event not found` 경고만 내고 키를 버린 채 «Complete». 스켈레톤 병합(`--merge`)으로도 정의가 넘어오지 않는다 |
| 4.3.26, 실제 작업 파일(cat 복사본) 애니메이션 무변경 교체 | 됨. JSON 완전 동일. 단 cat에는 이벤트 정의가 없어 이 경로로는 이벤트를 넣을 수 없다 |

주의: CLI가 프로젝트를 다시 저장하므로 포맷이 실행 버전으로 올라간다(4.3.00·4.2.43 → 4.3.26). JSON에 없는 해당 애니메이션의 에디터 전용 정보는 확인하지 않았다. 실시간도 아니다(에디터를 닫고 해야 한다).
